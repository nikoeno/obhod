## Session 3: generated configs

- [high] internal/pc/singbox/singbox.go:148-160 (golden `testdata/mixed.golden.json:157-171`): route rules are emitted one rule per route in the fixed order proxy, tunnel, desync, direct, but sing-box takes the first matching rule. `route.Table.Lookup` promises the longest suffix wins (`internal/lib/route/API.md`), so a more specific entry is shadowed by a less specific one with a higher-priority route. The golden shows it: `a.yt.example` is `direct` in the table, but the earlier `yt.example → desync` rule matches it first. The same happens for a `direct` or `desync` child of a `tunnel`, `proxy` or `block` parent (for example `tunnel example.com` + `direct cdn.example.com` sends the CDN through the tunnel, and a `block` parent blocks every child). The fixture `singbox_test.go:36-41` contains this overlap and the golden blesses the result. (confirmed from the golden and rule order; first-match semantics of sing-box not exercised at run time)
- [medium] internal/pc/singbox/singbox.go:162-172, 182: DNS leak of non-A/AAAA types, see "Input for decisions" D1. For a tunnel domain, every query type except A, AAAA, HTTPS and SVCB reaches the direct DoH server. (confirmed)
- [medium] internal/pc/singbox/singbox.go:163-165: the same overlap problem in DNS: a tunnel or proxy domain below a direct or desync suffix (`x.example.com` tunnel, `example.com` direct) is resolved by `dns-direct` for all query types, so it gets the real (possibly poisoned) IP instead of FakeIP and the name leaks. ## Input for decisions

### D1: which query types of a tunnel domain can reach the direct DoH server

DNS rule order in `singbox.go`: (1) lines 163-165, domains routed `direct` or `desync` → `dns-direct`; (2) line 170, `HTTPS`, `SVCB` → reject; (3) line 171, `A`, `AAAA` → `dns-fakeip`; the default (`final`, line 182) is `dns-direct`. Therefore, for a domain that is not under a direct/desync suffix (tunnel, proxy, block, or unknown):
- Reach `dns-direct` (the leak): every other type, for example `TXT`, `MX`, `NS`, `SOA`, `CNAME`, `SRV`, `CAA`, `PTR`, `NAPTR`, `TLSA`, `SSHFP`, `DS`/`DNSKEY`, `ANY`. Apps normally send `TXT` (SPF/verification, some CDNs), `MX` (mail clients), `SRV` (Teams, XMPP, Minecraft) and `CAA`, so the name can leak in ordinary use.
- Do not reach it: `A`, `AAAA` (FakeIP), `HTTPS`, `SVCB` (rejected).
- Also reach it, for every type including A/AAAA: a tunnel/proxy/block domain that is below a direct/desync suffix in the table (rule (1) matches the suffix; see Session 3).
- Also reach it by design: the DoH server and the tunnel server's own host name resolution (`default_domain_resolver`, `singbox.go:200`); LAN-resolver queries bypass the TUN altogether (Session 3).
Where the rules live: `singbox.go:162-172` (rules), `:176-184` (servers, `final`, `strategy`). Test coverage: only the golden `mixed.golden.json:4-29`.
Cost facts for the choice: rejecting other types needs one more rule (`query_type` list or "everything except A/AAAA" via a catch-all `reject` before `final`) and breaks anything that needs those records for tunnel domains (mail clients, SRV based apps would see no answer); routing them through the tunnel needs a DNS server whose `detour` is `tunnel` (not configured now, and the DNS server entry is a new config field/contract change).

### D2: normal traffic that triggers each monitor heuristic

What a flag does downstream: `ReportFailure` accepts it only for a non-static table entry whose current route equals the reported route (`checker.go:256-268`); 3 reports for the same (network, domain, route) within 5 min schedule a recheck of that domain (`schedule.go:61-76, 345-363`). It never changes a route by itself. Cost: probes against that domain.

- `TLS_RST` (`detect.go:46`: TCP, 1 B-4 KB up, at most 64 B down, age at last sighting up to 2 s, then the connection disappears):
  - a normal request that finished between two polls after being seen only in its handshake (confirmed, Session 4);
  - TLS connections the server answers with an alert (7 B) or a short close: unsupported SNI/ALPN, a server that rejects the client hello;
  - a tab or app that aborts a request right after sending the client hello (cancelled navigation, preconnect that got data once);
  - connection refused or host unreachable on the remote side (sing-box accepts in the TUN, receives the client hello, the dial fails fast): up-only, down 0;
  - tiny request/response protocols closed within 2 s: MQTT connect and CONNACK (push services), a health check or `HEAD` with a 204/304 response under 64 B, SMTP/IMAP greeting probes.
- `TCP_TIMEOUT` (`detect.go:49`: TCP, 0 B both ways, closed after 5 to 30 s):
  - browser preconnect or speculative sockets that were never used (confirmed);
  - an app that opens a socket and waits for the server to speak first (some game, IoT and mail clients) and then gives up;
  - a connection waiting while the remote end is down (a real timeout, this is the intended case);
  - sing-box sniff waits, and a connection that sing-box accepted but whose outbound dial is still pending.
- `STALL_16_20` (`detect.go:61`: TCP, 12-36 KB downloaded, connection age and idle time at least 10 s):
  - an HTTP/2 or HTTP/1.1 keep-alive connection kept open after a small page or an API reply of 12-36 KB (confirmed): the common case on most sites;
  - a long poll or a websocket whose traffic is sparse after an initial burst; a chat or notification connection with heartbeats shorter than 10 s is not flagged, longer ones are;
  - a paused video or a download the user paused;
  - a stalled flow after a Wi-Fi switch.
